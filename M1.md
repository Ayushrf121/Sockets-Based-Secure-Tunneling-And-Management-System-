## 3. Design

### 3.1 User model

`User` is a Java `record`, so it is immutable. To change a user (for example to
disable an account), `withEnabled(boolean)` returns a modified copy, which the
store then saves with `update()`.

Roles are `ADMIN` and `USER`.

### 3.2 Password hashing (bcrypt)

- Algorithm: **bcrypt**, cost factor **12** (about 4,096 rounds of the key schedule).
- A random salt is generated per password and embedded in the hash, so the same password produces a different hash each time.
- Bcrypt is deliberately slow, which makes brute-force attacks expensive.
- Verification catches malformed hashes and returns `false` instead of throwing.

Hash format: `$2a$12$<22-char salt><31-char hash>`

### 3.3 Storage abstraction

```java
public interface UserStore {
    Optional<User> find(String username);
    boolean add(User user) throws IOException;
    boolean remove(String username) throws IOException;
    boolean update(User user) throws IOException;
    List<User> list();
}
```

The server will depend only on this interface. In Phase 2 a database-backed
implementation replaces `FileUserStore` and nothing else changes.

### 3.4 File format

One user per line, pipe-separated. Lines starting with `#` are comments.

```
# username|bcrypt_hash|ROLE|enabled
alice|$2a$12$...|USER|true
admin|$2a$12$...|ADMIN|true
```

### 3.5 Safety measures in `FileUserStore`

| Concern | Measure |
|---|---|
| Corrupted file on crash | Writes go to a `.tmp` file first, then replace the real file |
| Concurrent access from threads | All public methods are `synchronized` |
| File-format injection | Usernames must match `[A-Za-z0-9_]{3,32}`, so `\|` and newlines are impossible |
| Duplicate users | `add()` returns `false` if the username exists |

Run `Milestone1Demo` (temporary class) and confirm:

1. A duplicate user is rejected.
2. The correct password returns `true`, a wrong one returns `false`.
3. Disabling a user is reflected in the store.
4. The generated file contains only bcrypt hashes.

## 5. Security notes

- Plain-text passwords exist only in memory while being hashed or verified.
- The user file contains hashes only. Even so, it is git-ignored (`users.db`) and should be readable only by the server.
- Bcrypt uses only the first 72 bytes of a password. A minimum and maximum length policy will be enforced at the protocol layer in Milestone 3.
