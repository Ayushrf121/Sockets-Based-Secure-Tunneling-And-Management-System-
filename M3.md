# Milestone 3: Login, Lockout and Admin Console

**Project:** Secure Proxy (PBL)
**Phase:** 1 (CLI version)
**Package:** `com.secureproxy`
**Depends on:** Milestone 1 (users, bcrypt) and Milestone 2 (TLS channel)

---

## 1. Objective

Only registered users may use the server. After the encrypted TLS connection is
established, a client must log in with a username and password. The server
checks the password against the bcrypt hash stored by Milestone 1.

Goals:

- Login messages use a simple, documented JSON protocol.
- The password travels only inside the TLS connection and is verified with bcrypt on the server. The client never sends a hash.
- Repeated wrong passwords lock the username and the IP address for a while.
- An admin creates and manages users from a console on the server machine.
- Everything that can be unit-tested is tested.

## 3. Protocol

One JSON message per line, over the TLS connection. Fields that are not needed
are left out.

| Direction | `type` | Other fields | Meaning |
|---|---|---|---|
| Client to server | `LOGIN` | `username`, `password` | Log in |
| Server to client | `LOGIN_OK` | `username`, `role` | Login accepted |
| Server to client | `ERROR` | `code`, `message` | Something failed |
| Both ways | `PING` / `PONG` | none | Test the link |
| Both ways | `WHOAMI` | `username`, `role` in the reply | Ask who you are logged in as |
| Both ways | `ECHO` | `text` | Server sends the same text back |
| Client to server | `LOGOUT` | none | Leave |
| Server to client | `BYE` | none | Goodbye, connection closes |

### Error codes

| Code | When |
|---|---|
| `AUTH_FAILED` | Unknown user, disabled user or wrong password (all look the same on purpose) |
| `LOCKED` | Too many failed attempts for this username or this IP |
| `TOO_MANY_ATTEMPTS` | 3 failed logins on one connection |
| `LOGIN_REQUIRED` | A message other than `LOGIN` before logging in |
| `BAD_REQUEST` | The line was not valid JSON or had no `type` |
| `ALREADY_LOGGED_IN` | `LOGIN` sent again during a session |
| `UNKNOWN_TYPE` | Unrecognised message type |
| `ACCOUNT_DISABLED` | The account was disabled or removed during the session |

### Example conversation

```
C: {"type":"LOGIN","username":"alice","password":"GoodPass123"}
S: {"type":"LOGIN_OK","username":"alice","role":"USER"}
C: {"type":"ECHO","text":"hello"}
S: {"type":"ECHO","text":"hello"}
C: {"type":"WHOAMI"}
S: {"type":"WHOAMI","username":"alice","role":"USER"}
C: {"type":"LOGOUT"}
S: {"type":"BYE"}
```

## 4. Connection phases

```
TLS handshake (10 s)  ->  Login (30 s, max 3 tries)  ->  Session (5 min idle limit)
```

At the start of every session message the server checks the account is still
active. If an admin disables or removes a user, that user's session ends on
their next message.

---

## 5. Security design

| Concern | Measure |
|---|---|
| Learning which usernames exist | Unknown user, disabled user and wrong password return the same `AUTH_FAILED` message |
| Timing differences | For unknown or disabled users the server still runs a dummy bcrypt check, so the response takes about the same time |
| Password guessing on one account | 5 failures lock that username for 15 minutes |
| Guessing across many usernames | 10 failures lock the source IP for 15 minutes |
| Lockout revealing real accounts | Unknown usernames are counted and locked exactly like real ones |
| Guessing while locked | Passwords are not checked at all during a lock |
| IP counter reset by logging in as yourself | A successful login clears the username count but never the IP count |
| Memory exhaustion by endless lines | Lines over 4096 characters disconnect the client |
| Memory exhaustion by many fake usernames | The limiter purges old entries when it grows past 10,000 |
| Connection hogging | Handshake and login time limits; at most 20 workers and 10 waiting connections, then new ones are refused |
| Passwords in logs | Raw lines are never logged and `Message.toString()` hides the password |
| Fake log lines | Usernames are shortened and unusual characters replaced before logging |
| Weak new passwords | At least 8 characters; at most 72 bytes (bcrypt ignores the rest); no control characters; not equal to the username |
| No default account | The first user is created from the admin console. No built-in password exists. |

## 6. Where the data is saved

Users are saved in **`users.db`** in the folder the server was started from. If
you start the server from the project root, that is `D:\Secure_Proxy_PBL\users.db`.
The server prints the full path when it starts.

- The file does not exist until the first user is created.
- It contains bcrypt hashes only, never plain passwords.
- It is listed in `.gitignore`.
- Lockout counters are kept in memory only, so they reset when the server restarts.

## 7. How to run

```powershell
# Terminal 1 - server (certificates from Milestone 2 must already exist)
$env:PROXY_TLS_PASS = "your-password"
mvn compile
mvn exec:java "-Dexec.mainClass=com.secureproxy.server.TlsServer"

# at the admin> prompt:
adduser alice
adduser boss admin
listusers

# Terminal 2 - client
$env:PROXY_TLS_PASS = "your-password"
mvn exec:java "-Dexec.mainClass=com.secureproxy.client.TlsClient"
```

### Admin console commands

| Command | Meaning |
|---|---|
| `adduser <name> [admin\|user]` | Create a user (asks for the password twice) |
| `passwd <name>` | Change a password |
| `listusers` | Show users, roles and whether they are enabled |
| `disable <name>` / `enable <name>` | Block or allow login |
| `removeuser <name>` | Delete a user |
| `exit` | Stop the server |

### Client commands

| Command | Meaning |
|---|---|
| any text | Sent as `ECHO`; the server sends it back |
| `/whoami` | Show your username and role |
| `/ping` | Test the connection |
| `/logout` | Leave |
| `/help` | List commands |

## 9. Known limitations

| Limitation | Why it is acceptable for now | Planned fix |
|---|---|---|
| Anyone can lock a known username by failing 5 times | Common trade-off; the IP lock and 15-minute limit reduce harm. A locked admin can still use the server console. | Phase 2: progressive delays and per-IP plus per-user keys |
| No session token; the TLS connection is the session | Simple and safe for a single long-lived connection | Phase 2 (GUI, reconnects) |
| Roles are stored but not enforced yet | There is nothing role-restricted so far | Milestone 4 |
| Admin console is local only | Avoids a remote admin attack surface | Phase 2 admin dashboard |
| Password is visible while typing if the terminal has no hidden-input support | Java limitation under some launchers | Phase 2 GUI |
| Lockout counters reset on restart | Memory only | Phase 2 (database) |
| `users.db` is a plain text file | Hashes only; file access is controlled by the operating system | Phase 2 (database) |
| No audit log file yet | Events are printed to the console | Milestone 4 |
